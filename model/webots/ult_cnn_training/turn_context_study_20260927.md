# 회전 원인 분리 점검 (2026-09-27)

## 출력 클래스와 상황 표식

FPGA 출력은 기존 6개 클래스(`직진`, `좌회전`, `우회전`, `급좌회전`, `급우회전`, `정지선`)를 유지한다. `차선 복귀`는 현재 별도 출력 클래스가 아니다. 흰 선이 화면 중앙까지 들어온 **차선 이탈 상태**에서도, 실차가 왼쪽으로 얼마나 강하게 조향해야 하는지에 따라 `좌회전` 또는 `급좌회전`을 붙인다. 오른쪽 복귀도 같다. 직각 코너, 급한 S자, 차선 복귀는 `scene_context`로 따로 기록한다. 같은 조향 출력으로 서로 다른 제어 절차를 적용해야 한다면 FPGA 클래스 외에 상황 정보나 라즈베리파이의 연속 영상 판단이 추가로 필요하다.

중앙 흰 선의 위치만으로는 이탈 복귀와 일반 곡선·교차로·정지선 근처를 구별할 수 없었다. [중앙 선 후보 영상](output/recovery_visual_candidates_20260927.png)에 오검출 사례가 함께 있다. 기존 수동 촬영에는 로봇 위치·회전 원인 표식이 없으므로 복귀 장면을 사후 자동 재라벨링하지 않았다.

## 이번 수집과 분할

- 학습용 16번 맵에서 꺾이는 지점이 보이는 급좌회전 3장·급우회전 5장을 추가했다. [검수 영상](output/visible_corner_capture_20260927.png).
- 같은 위치의 밝은 조명 8장은 16×16 입력이 기본 조명과 거의 같아 원본만 보관하고 학습 목록에서 보류했다. 15번 맵의 완만한 곡선 8장 중 위치가 사실상 중복된 4장은 보류하고 4장을 학습에 추가했다.
- 평가용 18번 맵에는 직각 코너 2개와 완만한 곡선 2개를 배치했다. 중앙 카메라에 코너가 보이는 자세를 미리 확인해 직각 좌·우 각 1장과 곡선 좌·우 각 2장을 평가 집합으로 기록했다. [맵 파일](../worlds/ult_auto_iro_test_18.wbt), [타일 배치](../track/iro_official_tiles/iro_lane_18_mixed_holdout_3m.png).
- 자동 수집기는 새 촬영부터 `scene_context`를 에피소드 기록에 보존한다. `corner_90`, `tight_s_curve`, `lane_recovery`, `gentle_curve` 등을 사용할 수 있다. 18번 맵의 6장은 `corner_90` 2장과 `gentle_curve` 4장으로 확인됐다. [맥락 목록](turn_context_inventory.csv).

현재 선별 목록은 1,592장으로 학습 1,042장, 개발 검증 385장, 외부 평가 165장이다. 서로 다른 분할 간 완전 동일한 16×16 입력은 0쌍이다([중복 검사](split_overlap_audit.json)). 18번 맵은 평가 전용이며 학습에 포함되지 않았다. 원본 공식 타일 그림을 다른 배치로 재사용했으므로 새로운 소재에 대한 독립 시험은 아니다.

## 다음 수집 기준

1. 차선 복귀는 흰 선이 중앙에 있다는 사실에 더해 차량이 차선을 벗어났다가 다시 들어가는 **연속 장면과 위치**로 확인한다. 복귀 방향과 필요한 실차 조향 강도를 출력 클래스로, 원인은 `lane_recovery`로 기록한다.
2. 직각 코너·급한 S자·복귀를 각각 충분히 확보하되, 같은 위치·각도의 연속 프레임을 대량 저장하지 않는다. 특히 이번 평가에서 실패한 직각 코너와 완만한 우회전의 위치·조명을 다양화한다.
3. 새 맵/실차 자료는 평가 전용으로 따로 남긴다. 16×16 입력에서 구분하기 어려운 장면은 원본과 연속 프레임을 함께 검토한다. 상황별로 필요한 제어 정책이 다르면 클래스 출력 설계를 다시 정한다.

## 차선 복귀 수집 준비

18번 맵의 위쪽 직선에서 로봇을 안쪽 흰 선 바깥(`map_y_px=310~340`, 흰 선 약 `260`)에 놓고 양방향으로 미리보기를 확인했다. 중앙 카메라에 흰 선이 크게 들어오는 위치가 확인됐다([미리보기 모음](../controllers/ult_auto_collector/preview/20260927T010723034972Z/review_sheet.png)). 지도 바깥 경계에 가까운 `map_y_px=0~20`은 벽이 카메라에 크게 보여 수집 위치에서 제외한다.

이 정지 미리보기만으로는 **차선을 벗어났다가 복귀하는 실제 연속 동작을 증명할 수 없어** 학습/평가 라벨을 추가하지 않았다. 이어서 아래의 실제 주행 경로를 촬영하고, 복귀 전후의 위치와 방향을 검수했다.

## 연속 복귀 예비 촬영 결과

우선 차선 바깥에서 출발해 안으로 돌아오는 양방향 경로를 확인했다([첫 연속 영상](../controllers/ult_auto_collector/preview/20260927T011011432532Z/trajectory_review_sheet.png)). 이어서 차선 안 `y≈150`에서 출발해 안쪽 경계선 `y≈260`을 넘어 `y≈281`까지 이탈하고, 다시 `y≈209`까지 복귀하는 **전체 이탈·재진입 경로**를 양방향으로 촬영했다. [전체 연속 중앙 영상](../controllers/ult_auto_collector/preview/20260927T011427036215Z/trajectory_review_sheet.png)과 [위치·촬영 시점 기록](../controllers/ult_auto_collector/auto_collection_status_20260927T011427036215Z.json)에서 실제 이동을 확인할 수 있다. 벽이 보이는 지도 바깥 경계는 사용하지 않았다.

전체 경로에서 복귀 조향이 시작되고 아직 경계선 바깥에 있는 각 주행의 2시점, 총 4프레임을 [복귀 후보 목록](recovery_candidate_manifest_20260927.csv)에 분리 보관했다. 지도상 진행 방향에 비추어 동쪽 주행의 필요한 **복귀 방향은 왼쪽**, 서쪽 주행은 **오른쪽**이다. 저장 모델 3종 모두 이 4프레임에서 방향을 1/4 맞혔다([예측 상세](recovery_direction_probe_20260927.json)). 두 경로의 연속 프레임이므로 독립 시험 4건이나 실제 주행 성공률로 해석하지 않는다. e-puck의 바퀴 속도로 실차 조향 강도를 정할 수 없으므로 일반/급회전 강도 클래스는 아직 붙이지 않았고, 기존 `training_manifest.csv`와 6클래스 평가 집합에도 추가하지 않았다.

다음 데이터 작업은 실차의 일반/급조향 기준을 영상과 조향량으로 먼저 고정한 뒤, 이 후보의 강도를 검수하고 학습용 지도에서 다양한 복귀 방향·위치·조명으로 연속 촬영하는 것이다. 새 촬영분은 주행 단위로 학습/평가를 나누고 중복된 연속 프레임을 솎는다.

## 좌우 반전 학습 실험

기존 학습 1,042장만 좌우 반전하고 좌·우 라벨을 교환해 총 2,084개 입력으로 별도 모델을 학습했다. 첫 모델(`output_mirror_20260927`)은 반전 후에도 원본 클래스 수로 손실 가중치를 계산한 실험이다. 개발 검증은 기준 모델(`output_visible_pair_20260927`)의 **222/385 → 248/385**로 늘었지만 일반 우회전은 **16/32 → 2/32**, 복귀 방향은 **1/4 → 0/4**로 악화됐다. 따라서 이 첫 결과를 반전 학습의 결론으로 사용하지 않는다.

가중치를 반전 후 클래스 수로 바로잡은 모델(`output_mirror_balanced_20260927`)도 별도 학습했다. 아래 수치는 기준 모델과 비교한 값이다.

| 평가 항목 | 기준 | 가중치 보정 반전 모델 |
| --- | ---: | ---: |
| 개발 검증 전체 | 222/385 | 237/385 |
| 개발 검증 일반 좌/우 | 8/16 · 16/32 | 6/16 · 7/32 |
| 개발 검증 급좌 | 4/44 | 22/44 |
| 공식 타일 | 45/87 | 53/87 |
| 반전 S자 | 9/22 | 15/22 |
| 새 18번 맵 | 2/6 | 4/6 |
| 복귀 방향 후보 | 1/4 | 1/4 |

18번 맵의 개선 2건은 모두 완만한 곡선이다. **직각 코너는 여전히 0/2**다([프레임별 결과](context_holdout_evaluation_20260927.json)). 일반 좌·우회전 오류가 늘고 복귀 방향은 개선되지 않아 이 모델도 채택하지 않는다. 외부 자료는 여러 실험에서 반복 비교했고 복귀 후보는 단 두 주행의 연속 프레임이므로 최종 성능 증거가 아니다([복귀 예측 상세](recovery_direction_probe_20260927.json)).

복귀 후보 네 장과 가까운 학습 16×16 이진 입력 다섯 장씩을 찾았더니 20개 모두 `직진` 라벨이었다([근접 입력 검토](output/recovery_neighbor_review_20260927.png)). 원본 영상에서는 좌우 흰 선 위치가 다르게 보이고 16×16 입력에도 그 차이가 남아 있다([복귀 입력 모음](output/recovery_16x16_20260927.png)). 이는 16×16에서 방향 구분이 원천적으로 불가능하다는 증거가 아니라, **확인된 차선 복귀 학습 사례가 부족하고 기존 라벨이 이 구도를 충분히 설명하지 못한다**는 근거다. 수동 촬영분에 복귀 장면이 있는지는 메타데이터가 없어 아직 확인되지 않았다.

설계 문서에는 **일반 좌·우회전 -30°/+30°, 급좌·우회전 -60°/+60°**의 명목상 조향값이 있다(`CNN 학습을 위한 Sim-to-Real 전이 학습 및 FPGA 가속기 통합 전략.pdf` 5쪽; `가성비 AI가속기 개발을 위한 ULT-CNN 적용 연구.pdf` 3쪽). 앞서 "프로젝트 파일에서 조향 강도 기준을 찾지 못했다"고 쓴 것은 잘못이었다. 이 각도는 설계 표의 목표값이며, 현재 실차에서 측정된 서보 각도라는 근거는 아니다. 문서에는 **차선 복귀 영상이 ±30°와 ±60° 중 어디에 해당하는지** 판정하는 규칙도 없다. 사용자가 확정한 구조에 따라 FPGA는 클래스만 전달하고 라즈베리파이가 실제 조향값을 정한다. `drivetest2.py`는 7/9와 4/6을 별도 문자 명령으로 전송하지만 서보 각도·PWM 매핑, 차량 속도·회전 반경 기록은 없다. Webots e-puck 제어 코드의 ±0.25/±0.55 값도 실차의 조향각이 아니다.

실차 측정 시에는 같은 속도와 바닥에서 `7=일반 좌`, `4=급좌`, `9=일반 우`, `6=급우`를 각각 짧게 구동해 **실제 서보 각도 또는 PWM 값, 주행 거리, 회전 반경, 카메라 영상**을 한 세트로 기록한다. 이후 복귀 후보의 필요한 경로가 일반 명령으로 가능한지, 급회전 명령이 필요한지 판단한다. 좌·우 방향 정답은 이미 지도 위치로 확인됐으므로 강도 경계만 이 측정으로 확정하면 된다.

장치 확인 시 Windows에 COM4(CH340)의 과거 장치 항목은 남아 있었으나 상태가 `Unknown`이고, 현재 연결된 포트 목록에는 나타나지 않았다. 따라서 이 환경에서 물리 차량의 실제 조향값을 읽거나 측정하지 않았다. 설계상 ±30°/±60°와 실차 보정값을 혼동하지 않는다.
